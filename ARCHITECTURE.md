# Архитектура (проектное решение, до реализации)

## Технологии
Next.js App Router + TypeScript strict, React, собственный CSS/CSS Modules и токены; GSAP только там, где нужен. PostgreSQL + Prisma (миграции и SQL для ограничений, не заменять их проверками UI). Zod или эквивалент для серверной валидации, Recharts для аналитики, Playwright для E2E, Vitest для unit/integration, ESLint. Node.js LTS и совместимые актуальные версии выбрать при bootstrap, зафиксировать lockfile. Один full-stack проект + отдельный worker из того же репозитория (дешевле микросервисов). Docker Compose для локальной БД и по необходимости для деплоя; Linux VPS в РФ, HTTPS reverse proxy (Caddy/Nginx), PostgreSQL закрыт от публичной сети. Локальные команды npm run dev/build/lint/typecheck/test/test:e2e документировать. Не устанавливать лишние зависимости.

## Предлагаемая структура
app/(public)/... — сайт, app/admin/... — CRM, app/analytics/... — аналитика, app/api/... — HTTP endpoints, components/public и components/admin, lib/domain (правила), lib/server (DB, auth, integrations), lib/validation, prisma/schema.prisma и migrations, worker/ (outbox + сводки), public/assets/, tests/, docs/review/, docs/assets-register.md. Разделить публичные DTO и внутренние модели; server-only imports для секретов. Модульные границы и тестируемые сервисы. Модули: content/menu, booking, feedback/events, promotions, auth/rbac, analytics, notifications, calltracking, reporting.

## Основные сущности
RestaurantSettings (timezone, hours, exceptions, contact, trial dates); User, Role, Session, TelegramBinding; Category, Dish, MediaAsset, ContentBlock; DiningTable (capacity, zone, optional coordinates, active); Booking (id, public token hash, contact fields, guest count, source, requested interval, assigned interval/table, status, actual guest count, final bill, consent version/time, timestamps); BookingAlternative; BookingStatusHistory; Feedback, EventInquiry; Offer, PromoCode, Redemption; AnalyticsEvent, CallEvent; NotificationOutbox, DeliveryAttempt; AuditLog. Индексы на время, статус, source, уникальные slug, event_id/call_id и idempotency key. Деньги integer minor units. UTC timestamps (timestamptz). Контактные данные отделять от агрегатов и ограничивать выдачу.

## Бронирование и конкурентность
Pending = заявка, не подтверждение; pending не блокирует столик по умолчанию. confirmed/arrived занимают назначенный интервал; завершенные исторические записи не переписывать без аудита. PostgreSQL exclusion constraint (btree_gist + tstzrange, [start,end), по table_id, для активных статусов) или эквивалентное доказуемое атомарное ограничение; если расширение недоступно — транзакционные блокировки по столу + обязательный concurrency test. Буфер включить в интервал. Внутри транзакции проверить capacity, hours, пересечения, статус, обновить историю, поставить событие/уведомление в outbox. При конфликте 409 с понятным текстом. Для групп > вместимости — ручная обработка, не назначать неподходящий стол. Объединение столов только после согласования.
Переходы: pending → confirmed / alternative_proposed / rejected / cancelled. alternative_proposed → pending (новый запрос) / confirmed (если гость принял и слот доступен) / rejected / cancelled. confirmed → arrived / cancelled / no_show. arrived → completed. Перенос confirmed оформить отдельным предложением, сохраняя исходную бронь до атомарной смены интервала. Коррекция ошибки только уполномоченным сотрудником с причиной и аудитом. Идемпотентность create/confirm, optimistic version для конкурентных изменений. Не использовать клиентское время как источник истины.

## HTTP и интеграции
GET public menu/content; POST bookings, feedback, event-inquiry, promo/issue; GET booking status по высокоэнтропийному токену (не индексируется, no-store, no-referrer; исключить из логов и аналитики). Защищенные admin endpoints CRUD, booking transitions, reports, redemption; /api/webhooks/telegram, /api/webhooks/calltracking; POST analytics events с allowlist. Стандартизированные ошибки и request_id без PII. Rate limit на сервере, honeypot/антиспам, ограничение размеров, идемпотентность. Webhooks проверяют secret/signature по документации провайдера, имеют защиту от повторов. Telegram: allowlist chat/user ID, server-side mapping role, callback ID без PII, отвечать на callback. Не размещать токен в URL клиентского приложения. Внешние интеграции за интерфейсами с локальным mock, production не симулирует отправку/звонки. Outbox: запись в бизнес-транзакции, worker с leasing/retry/backoff, dead letter и ручной повтор, мониторинг; избежать дублей при повторном callback, внешняя доставка at-least-once.
Коллтрекинг: provider adapter + нормализация статусов и timestamps; webhook если доступен или периодический импорт с dedup. Подключение после выбора и теста провайдера. Запись звонков отключена. Не менять официальный контакт без согласования.

## Безопасность и персональные данные
Серверная авторизация на всех admin endpoints и server actions; deny-by-default RBAC, проверка объекта. Надежный password hashing (Argon2id или безопасный механизм выбранной библиотеки), secure HttpOnly SameSite cookies, CSRF для мутаций, истечение/отзыв сессий, защита входа и 2FA для owner при возможности. Нет публичной регистрации администраторов. Bootstrap владельца через локальную команду с безопасной передачей секрета. CSP, XSS prevention, security headers, no-store для приватных данных, SQL parameterization, safe media uploads, журнал без секретов. .env не коммитить, .env.example с именами параметров, секреты в окружении. Не сохранять пользовательские данные в GitHub, screenshots, внешних багтрекерах, Telegram. Минимизировать PII и исключить из observability. Политика хранения/удаления согласуется с оператором, включая резервные копии, экспорт и права субъектов. Для РФ предусмотреть первичный сбор и хранение ПД на территории РФ, отдельное информирование и основания обработки, договор с обработчиком, проверить уведомление РКН/согласие/трансграничную передачу до запуска с юристом/оператором. Не считать этот документ юридической консультацией. Метрика и любые сторонние скрипты подключаются после согласования законных оснований и настроек; не на страницах PII. PWA: кэшировать только публичные/статические ресурсы, не CRM и не страницу статуса.

## Деплой и наблюдаемость
Локальное, staging (не публично индексируемое, защищенное), production — раздельные базы и токены. Демо только синтетическое. CI lint/typecheck/tests/build, без production secrets. Миграции проверять перед продакшеном, бэкап перед изменением. Ежедневные зашифрованные бэкапы БД и медиа с согласованным сроком хранения, проверка восстановления. Health endpoint без деталей секретов, structured logs, сбои outbox/DB, uptime, лимиты диска; тестовые события исключаются. План rollback, HTTPS, firewall, ограниченный SSH. Не деплоить без согласования и приемки.
