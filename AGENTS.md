# Обязательные инструкции для Codex

## Миссия
Создать авторский, премиальный, коммерчески эффективный сайт «Вместо Кекса» с работающей системой бронирования и CRM. Не генерировать очередной шаблон. Перед любой работой прочитать README, DESIGN, REQUIREMENTS, ARCHITECTURE, ROADMAP, QA, PROGRESS. При противоречии остановиться на затронутой задаче, описать конфликт, запросить решение; требования безопасности обязательны. Не считать демонстрационные данные утвержденными.

## Рабочий процесс
1. Проверить git status и актуальность ветки; не стирать чужие локальные изменения, не применять force push. Работать на отдельной ветке feature/<этап>. Начинать с ближайшего незавершенного этапа ROADMAP, не выполнять весь продукт за один проход.
2. Перед изменениями кратко изложить план и критерии приемки; реализовать только текущий этап. Вопросы по отсутствующим ресурсам не блокируют создание явно обозначенного локального прототипа.
3. Визуальный этап: создать страницу, открыть в реальном браузере (Playwright или доступный браузер), снять скриншоты 1440×900, 1280×800, 390×844 и 360×800, проверить отсутствие горизонтального скролла. Сравнить с DESIGN, минимум один цикл визуальной доработки. Не выдавать наличие кода за проверку визуального качества. Скриншоты без персональных данных разместить в docs/review/<stage>/ либо приложить в PR. Если браузер недоступен, явно записать блокер.
4. Запустить применимые lint, typecheck, unit/integration/e2e, build; записать точные команды и результаты, не утверждать прохождение непроведенных тестов.
5. Обновить PROGRESS: статус, фактические изменения, команды, результаты, ограничения, открытые вопросы, ссылки на скриншоты. Сделать небольшие коммиты, отправить ветку в GitHub и открыть PR, если доступно. Дождаться человеческой приемки перед переходом к следующему этапу или merge. При отсутствии доступа к GitHub сообщить, а не симулировать публикацию.
6. Не запускать деплой, платные API, создание публичных аккаунтов, рассылки, реальную бронь или изменение рабочего ресторана без отдельного согласования.

## Визуальные запреты
Никаких AI-изображений еды, интерьера или людей; никакого стороннего stock, выдаваемого за ресторан; никаких готовых ресторанных тем, однообразных карточек, бессмысленных иконок, градиентов, glassmorphism, чрезмерных скруглений, фальшивых наград и отзывов. Не менять логотип и палитру без согласования. Использовать только подтвержденные материалы с правами; если их нет — нейтральные явно подписанные placeholders в локальном прототипе, не имитация ресторана. Не использовать публичные URL картинок как постоянный hotlink. Вести реестр происхождения ассетов. Все публичные тексты на русском, без общих маркетинговых клише. Не прятать цены и действия за hover.

## Инженерные запреты
Никаких секретов в репозитории/клиентском JS/логах; .env.example только с пустыми значениями. Не передавать персональные данные в аналитику, GitHub, Telegram или внешние тестовые системы. Тесты — синтетические. Не подделывать метрики, статусы платежей и бронирований. Не считать нажатия звонками, просмотры продажами, а заявки приходом гостей. Не внедрять скрытое наблюдение, запись разговоров, агрессивный сбор идентификаторов. Ограничивать доступ по роли на сервере. Не отключать проверки безопасности ради демо.

## Решения
Telegram — главный канал уведомлений сотрудников; PWA/web push — независимый опциональный канал. WhatsApp Business API и платные SMS вне MVP. При недоступности Telegram CRM продолжает работать. Не обещать автоматические сообщения гостям в Telegram, если они не начали диалог. Не вводить оплату/доставку/кассу в MVP. Не считать наличие интеграционного адаптера фактическим подключением.

## Definition of done
Реализация + проверка + доказательства + запись прогресса + PR/коммит + явные ограничения. Внешний вид утверждает пользователь, не Codex сам. Не переносить этапы в статус «принято» без подтверждения.
